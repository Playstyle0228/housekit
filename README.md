# HouseKit — 烏日新成屋實質成交單價與回檔走勢

以內政部實價登錄原始資料，自動產製台中實質成交單價的月／季走勢，
分全國／縣市／行政區／生活圈四個層級共 9 個統計範圍，可自由勾選互相比較。

零第三方依賴（純 Python 標準庫），資料每月 1／11／21 日由 GitHub Actions 自動更新。

---

## 快速開始

```bash
python scripts/ingest.py --backfill    # 一次性回填 111S4 起所有季檔（約 1.8 GB 下載）
python scripts/aggregate.py            # 產製 docs/data.json
python -m http.server -d docs 8000     # 本機預覽 http://localhost:8000
```

日常更新只需（CI 也是跑這兩行，下載量約 14 MB）：

```bash
python scripts/ingest.py               # 只抓尚未收錄的旬檔
python scripts/aggregate.py
```

## 新增統計範圍

行政區層級幾乎零成本（持久層已有全市門牌）；生活圈層級需先查該區路街的里別：

```bash
python scripts/geocode.py 西屯區       # 查里別，累積寫入 data/street_li.json
# 在 zones.py 的 DISTRICTS 加一列；要生活圈就再到 ZONES 加，附上認定依據
python scripts/aggregate.py           # 重新聚合
```

`geocode.py` 用 OpenStreetMap Nominatim，依其政策每秒 1 次請求，一個行政區
約 150～250 條路街、3～5 分鐘。這是**一次性離線作業**——`zones.py` 只讀
`data/street_li.json`，執行期與 CI 都不呼叫外部服務。

前端的序列清單、顏色、晶片分組全部由 `data.json` 的 `meta.series` 決定，
新增區域不需要改 `index.html`。

## 部署與更新

GitHub Pages：repo Settings → Pages → Source 選 `main` 分支的 `/docs` 目錄。
`docs/index.html` 以相對路徑讀取同目錄的 `data.json`，無需後端。
**設定過一次之後，每次 push 都會自動重新部署，不需要再手動操作。**

線上位置：<https://playstyle0228.github.io/housekit/>

### 三種刷新方式

| 方式 | 觸發 | 下載量 |
|---|---|---|
| 自動排程 | 每月 1／11／21 日台北時間 10:00 | 約 14 MB |
| 手動 | Actions → `sync-plvr` → Run workflow | 約 14 MB |
| 手動＋補季檔 | 同上，勾選 `backfill` | 約 1.8 GB |
| 本機 | `python scripts/ingest.py && python scripts/aggregate.py` | 約 14 MB |

修改 `scripts/**`（例如調整 `zones.py` 的商圈範圍）並 push 後，workflow 也會
自動重新聚合，避免 `docs/data.json` 與程式脫節。

無新資料時不會產生 commit：`aggregate.py` 會比對現有 `docs/data.json`
（排除 `generated_at`），內容一致就不動檔案，因此 CI 不會留下一堆只有
時間戳不同的 commit。每次執行結果都寫進 Actions 的 Job Summary。

## 資料來源

內政部不動產成交案件實際資訊資料供應系統（`plvr.land.moi.gov.tw`），
使用「不動產買賣（成屋）」A 檔。三種端點與實測結果：

| 端點 | 內容 | 實測大小 | 保留期 |
|---|---|---|---|
| `DownloadHistory?type=season&fileName=115S2` | 全國一季 zip（756 檔） | 94～170 MB | 101S1 起永久 |
| `DownloadHistory?type=history&fileName=20260821` | 全國一旬 zip | 13～19 MB | **僅最近 6 旬** |
| `Download?fileName=b_lvr_land_a.csv` | 單縣市當期一旬 CSV | 約 433 KB | 當期 |

檔名規則 `{縣市碼}_lvr_land_{類別}.csv`，`b` = 臺中市，
類別 `a` = 成屋買賣、`b` = 預售屋、`c` = 租賃。編碼 UTF-8 with BOM，
**CSV 第 2 列是英文欄名，必須跳過**。

季檔以**登記日期**而非交易日期切分（如 115S2 = 登記 115/3/11～6/10），
因此跨季合併必須以「編號」欄去重。

伺服器雖回應 `Accept-Ranges: bytes`，但實測帶 `Range` 仍回 200 與完整長度，
**無法對 zip 做部分讀取**，只能整份下載。

## 架構

```
scripts/fetch.py       下載層：期別清單解析、zip 取用、登記期間推算
scripts/clean.py       清洗層：實質單價、屋齡、遞延與特殊交易剔除
scripts/geocode.py     一次性離線作業：查路街的里別 → data/street_li.json
scripts/zones.py       分區定義：行政區與生活圈，讀 street_li.json 做兩段式對照
scripts/store.py       持久層：data/records.csv.gz + data/state.json
scripts/ingest.py      下載並清洗新來源，寫入持久層
scripts/aggregate.py   聚合成 docs/data.json（月頻＋季頻）
docs/index.html        前端，讀取同目錄 data.json
legacy/                原始 Apps Script 原型（資料為手填佔位值，僅存參考）
```

### 為什麼要有持久層

1. 旬檔只保留最近 6 旬，過期即無法取得，必須自行留存。
2. 季檔每份逾百 MB，CI 每次重下 1.8 GB 不現實；持久層讓 CI 只需下載新增旬檔。
3. 持久層保留台中**全市**門牌（`addr`）與行政區（`dist`），因此**新增行政區或
   調整生活圈範圍只要重跑 `aggregate.py`，不必重跑回填**。

`data/records.csv.gz` 目前約 34 萬筆、7.0 MB，依（交易月, 編號）排序寫出，
使 git diff 穩定。`data/street_li.json` 是逐號里別對照表，也納入版控——CI 需要
它才能分區，而重建成本約 27 分鐘。

## 指標定義

**實質單價（萬元／坪）**

```
(總價元 − 車位總價元) ÷ ((建物移轉總面積 − 車位移轉總面積) × 0.3025) ÷ 10000
```

先自總價與面積扣除車位再換算坪單價，避免含車位案件壓低單價。

**新成屋**：屋齡 = 交易年月 − 建築完成年月 ≤ 5 年。
每個分區同時輸出 `new`（新成屋）與 `all`（全屋齡）兩組，前端可切換。

**代表值**：中位數。樣本少時較平均數穩健、不受少數高單價個案拉動；
另輸出 P25／P75 與樣本數 n。

前端「取值」可切換單期或 **3 期合併**。合併是把視窗內各期的*交易明細倒在一起*
後取中位數，而非對各期中位數再平均。低樣本分區（明道商圈每季僅 5～16 筆）的
單期中位數鋸齒劇烈，合併後才有可讀趨勢，且不會憑空造出資料點。
圖表一律以直線連接（`tension: 0`）—— 低樣本序列用曲線平滑會製造不存在的過衝。

**納入建物型態**：住宅大樓、華廈。排除透天厝、店面、廠辦等含大量土地價值、
單價不可比者。

## 期別口徑

**各期一律按「交易年月日」分月／分季，不是按登記日或揭露日。**

這件事會造成本專案數字與其他網站不同，務必留意：實價登錄的季檔本身是按
**登記日期**切分（115S2 = 登記 115/3/11～6/10），而季檔內的交易日期跨越數年。
同一批資料用兩種口徑統計，結果差異不小——以烏日全區新成屋為例：

```
登記季 115S2（登記 115/3/11~6/10）  n=89  中位 47.32 萬
交易季 115/Q2（交易 115/04~06）     n=71  中位 45.26 萬
兩者重疊僅 19 筆
```

本專案採交易日口徑，因為目的是反映「當月實際成交行情」；代價是最近數期的
樣本仍在累積（見下方尾端資料完整度）。

## 三道正確性控制

### 1. 交屋遞延剔除

實價登錄當期揭露資料中含大量數年前簽約、近期才登記的案件。實測 115/08 旬檔
台中市 1,162 筆中，僅 517 筆是 115/06～08 成交，其餘 645 筆是 109～114 年成交。

判準是**登記遞延月數**：來源檔的登記期間起始減去交易月，超過 6 個月即剔除。
以烏日區登記季 115S2 為例，不剔除為 43.38 萬／坪（n=183），剔除後為
**47.32 萬／坪（n=38）**，差 3.94 萬（9%）。

備註欄「預售屋、或土地及建物分件登記案件」曾被當作遞延的代理指標，
但只在烏日成立，已不採用，原因見下一節。

`clean.py` 另擋來源端鍵入錯誤的未來交易日（實測 111S4～115S2 共 3 筆，
含一筆民國 122 年）。

### 2. 特殊交易剔除

依 115S2 台中市備註分布歸納黑名單，見 `clean.py::SPECIAL_REMARKS`：
親友／員工／共有人等特殊關係、政府機關標讓售、協議價購、僅車位交易、
毛胚屋、公共設施保留地、畸零地、未辦繼承標售、權利讓渡、換約、抵債、瑕疵等。

黑名單**刻意不含**「預售屋、或土地及建物分件登記案件」。該備註曾被當作交屋
遞延的代理指標，但只在烏日成立：

```
烏日 115S2   有此備註 遞延 21~49 個月  ｜  無此備註 遞延 -2~7 個月   完全分離
南屯 115S2   有此備註 遞延  2~55 個月  ｜  無此備註 遞延 -2~57 個月  完全重疊
```

原因是該備註為「預售屋」**或**「土地及建物分件登記」，後者只是登記作業形式，
正常成屋交易也會出現。以它剔除會誤刪南屯遞延僅 2 個月的當期成交（115S2
單季 486 筆）。遞延一律交由上一節的登記遞延月數判斷。

### 3. 尾端資料完整度

最近數期樣本仍在累積（實測 115/07 全台僅 227 筆、115/08 為 0 筆，
正常月份約 1,700 筆）。若照原樣輸出，圖表尾端會出現純屬資料缺漏的假性崩跌。

以「全台全屋齡樣本數 ÷ 前 N 期樣本數中位數」為覆蓋率，
**只檢查尾端連續不足的期別**（避免誤判農曆年等真實淡季，如 115/02 n=1,133）：

- 覆蓋率 < 0.35 → 該期完全不輸出（記於 `meta.dropped_periods`）
- 覆蓋率 < 0.85 → 輸出但標記未定案（記於 `meta.provisional_months`）

### 4. 低樣本標記（而非隱藏）

樣本數 `0 < n < MIN_N`（預設 3）時**仍輸出中位數**，另以 `low` / `roll_low` 標記：
單筆成交的「中位數」就是那一筆本身、統計代表性有限，但它是真實成交價，不予隱藏。
前端以虛線線段＋空心放大點呈現，表格加琥珀底色與 ⚠，卡片轉琥珀色並在
現值或基準值任一為低樣本時降級提示。

只有 `n = 0`（該期完全無成交）才輸出 `null`，圖上呈現斷點，不做內插推估。

## 分區範圍

實價登錄成屋檔**沒有社區名稱或里別欄位**（只有預售屋 B 檔才有「建案名稱」），
只有門牌字串，因此分區只能靠路街名比對。但路街名要對到哪個生活圈不能憑印象，
本專案採「路街名 → 里 → 生活圈」兩段式對照，定義見 `scripts/zones.py`。

### 里別怎麼取得

`scripts/geocode.py` 逐一查詢資料中出現過的**每個門牌號**的里別
（OpenStreetMap Nominatim 結構化查詢），結果存 `data/street_li.json`。
`zones.py` 的 `li_of()` 逐筆解析：該號有實測值就直接用，否則取同路最接近的
已知號，再退到街道層級眾數。

必須逐號、不能只查路名，有兩個實測理由：

1. **只查路名不穩定且會判錯**。「烏日區公園路」兩次查詢分別回湖日里與烏日里；
   新興路的街道層級多數決落在湖日里而被歸入高鐵特區，實際屬舊市區。
   長路橫跨多里的規模是烏日 10 條／457 筆、南屯 59 條／3,639 筆。
2. **逐號查詢仍有孤立錯值**。「中山路一段 2 號」一次回前竹里、一次回九德里
   （實際距明道中學 974 公尺，前竹里在烏日南端）。因此 `zones.py` 的
   `_smooth()` 按號排序後取自身與前後各 `SMOOTH_WINDOW`（=2）個門牌的眾數，
   抹平孤立跳動而保留連續區段。實測修正 82／1,400 個門牌（5.9%），
   真實界線（新興路 616 號轉湖日里、健行路 798 號轉榮泉里）完整保留。

OSM 仍查無里別的路街以 `zones.py` 的 `FALLBACK` 人工補上，依據寫在該表註解裡。
`FALLBACK` **只補空缺、不覆蓋實測值**——曾憑字面把南屯「三和街」對到三和里，
門牌層級查詢實測為南屯里，路名與里名相近並不代表同屬。

### 生活圈

沿用樂居的生活圈劃分，並以公開的都市計畫範圍對照到里別。各生活圈的認定依據
寫在 `ZONES` 的 `basis` 欄位，會輸出到 `data.json` 供頁面說明顯示。

| 分區 | 里 | 依據 |
|---|---|---|
| 烏日全區／南屯全區 | 全部 | 行政區層級，不做門牌篩選 |
| 烏日高鐵特區 | 三和里、榮泉里、學田里、湖日里 | 都市計畫範圍：北以中山路三段延伸至高鐵路一至三段、東以高鐵東路、南以環河路四段五段、西臨長壽路 |
| 明道花園 | 九德里、仁德里 | 中山路一段與興祥街交叉口為中心、半徑約 700 公尺（舊地名「楓樹腳」） |
| 烏日車站 | 烏日里、東園里 | 舊市區，以中山路二段、新興路、光日路為主 |
| 烏日溪南 | 溪埧里 | 烏日南側，鄰霧峰、大里 |
| 南屯楓樹 | 楓樹里 | 樂居楓樹生活圈；位於烏日市區旁，以楓樹綠園道為核心的單純住宅區 |

樂居的「前竹重劃區」（烏日區前竹里）在 112/01 起的資料中無成交，故不產生序列。

未落入任一生活圈的門牌仍計入其所屬行政區序列。烏日區的生活圈涵蓋率
**100%**（1,624 筆全數歸類）；南屯區目前只定義一個生活圈（楓樹），
其餘 98% 僅計入南屯全區。

**沒有「南屯單元二」**：OSM 在南屯部分門牌的 `quarter` 欄位放的是重劃區名
（單元二自辦重劃黎明重劃區）而非里名，一度看來可直接當區界，但標籤極不一致
——新富路 7 個門牌只有 3 個帶此標籤。逐號解析後全區僅 14 筆帶標籤
（街道層級多數決時曾誤放大到 263 筆），覆蓋率過低且不成區段，故不建立序列。

### 明道花園的交叉驗證

以明道中學（中山路一段 497 號）為圓心量測，里別分類與樂居公布的 700 公尺
半徑定義互相印證：歸入明道花園的路街全數落在 700 公尺內，歸入烏日車站的
全數落在 700 公尺外。

### 為什麼沒有「十三期」

十三期市地重劃區只涵蓋豐樂里、楓樹里、樹德里、崇倫里、鎮平里各里的**部分**
區域，且跨南屯區與南區，無法以里別界定。以其四條界線路（東起西川一路、
西至環中路及南屯溪、南至建國北路、北抵文心南七路）的外接範圍實測：

```
豐樂里  框內  25 筆 / 框外 293 筆   命中率  8%
楓樹里  框內  39 筆 / 框外  67 筆   命中率 37%
鎮平里  框內  57 筆 / 框外  35 筆   命中率 62%
```

若以豐樂里代表十三期，會納入 293 筆實際位於文心南路、豐樂重劃區一帶的成交。
外接矩形本身也過於粗略——十三期並非矩形，其東南角落在南區崇倫里。要正確
切分需引入內政部市地重劃區範圍圖做點在多邊形判定，尚未實作。

## 已知限制

- **明道花園幾無新成屋供給**：屋齡結構偏舊，「新成屋」基準下 14 個季別只有
  4 期有值且皆為 n=1～2。跨區比較請切換至「全屋齡」才有可比性。
- 單一社區（如明道國際花園城，僑仁街 31 號、96 年完工）成交量過低，
  無法支撐任何頻率的序列，故本專案以生活圈為最小地理單位。
- **全台灣序列為 22 縣市合併中位數**，各期縣市組成變動會影響數值，
  僅作背景基準線參考，不等同官方住宅價格指數。
- 登記日 115/6/11～6/20 這 10 天目前兩種檔案皆未涵蓋（115S2 只到 6/10，
  現存最舊旬檔為 20260701）。115S3 季檔發布後，以
  `workflow_dispatch` 勾選 backfill 重跑即可補齊。
- **南屯區數字與樂居的落差尚未釐清**。以近一年（交易月 114/07～115/06）全屋齡
  中位數對照：烏日 41.84 萬 vs 樂居 41.76 萬（幾乎完全吻合，成交量 274 vs 449 筆），
  但南屯 38.79 萬 vs 樂居 52.51 萬（成交量 891 vs 1466 筆）。已排除的可能原因：
  「預售屋／分件登記」備註規則（修正後南屯近一年僅多 3 筆）、建物型態篩選
  （與樂居同為排除透天與公寓）。推測與時間基準有關——本專案按**交易日**分月
